7.6 RTOS – princíp a použitie

Embedded a reálne operačné systémy · 45 minút

Platforma a bezpečnosť: Pojem ?reálny operačný systém? v tomto tematickom celku označuje RTOS. Kódové ukážky FreeRTOS sú určené pre Arduino-ESP32 na Wokwi ESP32. Konkrétne piny, počet jadier, ADC a vlastnosti FreeRTOS závisia od modelu dosky a verzie frameworku. Pred zapojením overte pinout dosky; LED pripojte cez rezistor.

Trvanie: 45 minút
Nadväznosť: Úlohy, plánovač a synchronizácia.

Ciele hodiny

Žiak má vedieť:

  • navrhnúť jednoduché rozdelenie aplikácie na úlohy,
  • určiť základné časové požiadavky,
  • vybrať komunikáciu medzi úlohami,
  • porozumieť aplikácii s FreeRTOS na ESP32,
  • uviesť obmedzenia a riziká návrhu.

1. Čo nám RTOS poskytuje?

0 – 5 min

RTOS umožňuje aplikáciu rozdeliť na úlohy, ktoré:

  • vykonávajú svoju prácu,
  • čakajú na čas alebo udalosť,
  • odovzdávajú si údaje,
  • používajú spoločné prostriedky podľa pravidiel.

RTOS nenahrádza návrh aplikácie. Poskytuje mechanizmy na jeho realizáciu.

2. Návrh meracieho zariadenia

5 – 14 min

Zadanie:

  • každých 200 ms načítať analógový vstup,
  • odovzdať hodnotu komunikačnej úlohe,
  • vypísať ju cez sériový port.

Rozdelenie

ÚlohaČinnosťSpúšťanie
MeranieNačíta ADC a odošle hodnotu do frontyPravidelne
VýpisPrevezme hodnotu a vypíše juPri prijatí položky
ADC → úloha merania → fronta → úloha výpisu → UART/USB

Prečo fronta?

Oddeľuje okamih merania od okamihu výpisu.

Obe úlohy nemusia súčasne pristupovať k jednej premennej.

Čo určíme vopred?

  • periódu merania,
  • veľkosť fronty,
  • prioritu úloh,
  • reakciu na plnú frontu,
  • dostatočnú veľkosť zásobníkov.

3. ESP32: praktická aplikácia

14 – 30 min

Zapojenie

Pre klasickú vývojovú dosku s pôvodným ESP32:

  • potenciometer približne 10 kΩ medzi 3,3 V a GND,
  • jazdec na GPIO34.

GPIO34 je na pôvodnom ESP32 vstupný pin ADC1. Dostupnosť overíme na konkrétnej doske.

Ukážka zobrazuje surový kód ADC. Nepredpokladá presné meranie celého rozsahu 0 až 3,3 V.

Program pre Arduino-ESP32

Otvoriť Wokwi ESP32

#include <Arduino.h>

const int ADC_PIN = 34;

QueueHandle_t frontaMerani = nullptr;

void ulohaMerania(void* parameter) {
  TickType_t poslednyTermin = xTaskGetTickCount();

  for (;;) {
    int hodnota = analogRead(ADC_PIN);

    // Pri plnej fronte túto novú vzorku zahodíme.
    xQueueSend(frontaMerani, &hodnota, 0);

    vTaskDelayUntil(
      &poslednyTermin,
      pdMS_TO_TICKS(200)
    );
  }
}

void ulohaVypisu(void* parameter) {
  int hodnota;

  for (;;) {
    if (xQueueReceive(
          frontaMerani,
          &hodnota,
          portMAX_DELAY
        ) == pdPASS) {

      Serial.print("ADC: ");
      Serial.println(hodnota);
    }
  }
}

void chybaInicializacie() {
  Serial.println("Chyba vytvorenia RTOS objektov.");

  for (;;) {
    vTaskDelay(pdMS_TO_TICKS(1000));
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(ADC_PIN, INPUT);

  frontaMerani = xQueueCreate(8, sizeof(int));

  if (frontaMerani == nullptr) {
    chybaInicializacie();
  }

  // Najprv vytvoríme príjemcu.
  BaseType_t vypisOK = xTaskCreate(
    ulohaVypisu,
    "Vypis",
    3072,
    nullptr,
    1,
    nullptr
  );

  if (vypisOK != pdPASS) {
    chybaInicializacie();
  }

  BaseType_t meranieOK = xTaskCreate(
    ulohaMerania,
    "Meranie",
    2048,
    nullptr,
    2,
    nullptr
  );

  if (meranieOK != pdPASS) {
    chybaInicializacie();
  }
}

void loop() {
  vTaskDelay(pdMS_TO_TICKS(1000));
}

Vysvetlenie

Úloha merania

  • Má prioritu 2.
  • Pravidelne získava vzorku.
  • Posiela ju bez čakania do fronty.
  • Do ďalšieho termínu sa blokuje.

Úloha výpisu

  • Má prioritu 1.
  • Čaká na položku.
  • Pri prázdnej fronte nespotrebúva procesor kontrolnou slučkou.
  • Ako jediná v bežnej prevádzke používa sériový výpis.

Fronta

  • Uchováva najviac osem hodnôt typu int.
  • Kopíruje hodnoty.
  • Oddeľuje meranie od výpisu.

Zásobníky sú v použitom ESP32 prostredí zadané v bajtoch. Ich primeranosť sa v skutočnom projekte overuje meraním spotreby zásobníka.

4. Rozbor poruchových situácií

30 – 37 min

Výpis je pomalší než meranie

Fronta sa môže zaplniť.

V ukážke sa nová vzorka zahodí. V skutočnej aplikácii môžeme:

  • evidovať počet zahodených vzoriek,
  • zväčšiť frontu,
  • znížiť frekvenciu,
  • zmeniť prenos,
  • uchovávať iba najnovšiu hodnotu, ak staršie nepotrebujeme.

Meranie trvá príliš dlho

Pravidelné čakanie nedokáže nahradiť chýbajúci výkon. Treba zistiť, prečo úloha nestíha, a upraviť návrh.

Príliš malý zásobník

Môže poškodiť chod aplikácie alebo vyvolať diagnostickú reakciu podľa konfigurácie.

Príliš vysoká priorita

Úloha, ktorá sa neblokuje, môže obmedziť ostatné úlohy vrátane systémových.

Watchdog

Watchdog môže odhaliť niektoré druhy zaseknutia, ale neopravuje príčinu a nezaručuje správnosť meraní.

Čo meriame pri overovaní?

  • intervaly medzi vzorkami,
  • najdlhší čas vykonania,
  • zaplnenie fronty,
  • spotrebu zásobníkov,
  • reakciu na odpojenie periférie a chybu komunikácie.

5. Samostatný návrh

37 – 42 min

Navrhni systém regulácie teploty s tromi úlohami:

  1. snímanie teploty,
  2. regulácia ventilátora,
  3. zobrazovanie.

Urči:

  • ktoré činnosti sú pravidelné,
  • ako prenesieš teplotu,
  • ktorá úloha ovláda výstup,
  • čo sa stane pri neplatnom meraní.

Možné riešenie

ÚlohaNávrh
MeranieKaždých 500 ms odovzdá hodnotu aj stav platnosti
ReguláciaPrevezme meranie a nastaví požiadavku ventilátora
ZobrazeniePravidelne zobrazí stav, bez blokovania regulácie

Pri chýbajúcom alebo neplatnom meraní systém prejde do vopred definovaného chybového stavu.

Prioritu určujeme podľa časových a bezpečnostných požiadaviek. Neprideľujeme ju iba podľa poradia úloh v tabuľke.

6. Overenie a zápis

42 – 45 min

  1. Prečo príjemca čaká na fronte? Nemá prácu, kým nepríde údaj.
  1. Zaručí vyššia priorita presné vzorkovanie? Nie.
  1. Čo sa musí určiť pri plnej fronte? Konkrétna reakcia aplikácie.
  1. Je každý projekt vhodné rozdeliť na veľa úloh? Nie. Počet úloh má zodpovedať návrhu a dostupným prostriedkom.

RTOS poskytuje úlohy, plánovanie, časovanie a synchronizáciu.

Aplikáciu delíme podľa zodpovedností a časových požiadaviek.

Úlohy majú pri nečinnosti čakať na udalosť alebo čas.

Fronty umožňujú bezpečné odovzdávanie položiek.

Priority, zásobníky a kapacity frontov musíme navrhnúť a overiť.

Splnenie deadlineov závisí od celého systému, nielen od použitia RTOS.
